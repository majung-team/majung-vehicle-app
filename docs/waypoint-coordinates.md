# 경유지 좌표가 0으로 반환되는 문제

## 확인한 환경과 현상

공식 Pleos Connect Emulator 2.1.0 ARM64, NaviHelper 3.0.5에서 확인했다.
내비게이션 앱 버전은 `3.3.2-rc5-hotfix.3`이다.

좌표로 경유지를 추가한 뒤 `getWaypointInfo()`를 호출하면 경유지와 예상 시간은
반환되지만 위도·경도가 모두 0이었다. `addWaypoint()`와
`requestRouteWithWaypoints()`에서 같은 현상이 나타났다.
장소 ID를 함께 전달해도 좌표는 0이었다. 이 경우에는 응답의 장소 ID가 요청과 일치했다.

기존 시험에서는 경유지 예상 시간이 1020초, 최종 목적지가 1920초였다.
두 값이 다르므로 최종 목적지 예상 시간을 경유지 값으로 대신 쓰면 안 된다.

## 원인 조사에서 확인한 범위

설치된 공식 시스템 이미지에서 내비게이션 APK를 읽기 전용으로 확인했다.
마중 앱이나 연결 SDK에서 정상 좌표를 0으로 바꾸는 변환은 찾지 못했다.
내비게이션의 경유지 응답은 엔진의 경유지 좌표를 그대로 전달한다.

최종 목적지 응답에는 엔진 좌표가 0이면 원래 목적지 좌표를 사용하는 보정이 있다.
경유지 응답 경로에는 같은 보정이 없다. 이것은 최종 목적지만 정상 좌표를
반환하는 현상을 설명한다. 엔진 내부에서 좌표가 0이 되는 이유까지 입증한 것은 아니다.
제공 측 좌표 반환 문제와 마중의 대응을 구분한다.

APK·역컴파일 코드·원본 위치·장소 ID는 저장소에 올리지 않는다.

## 마중에서 처리하는 방법

최근 장소를 선택할 때 SDK가 함께 반환한 좌표와 장소 ID를 보관한다.
경유지 응답 좌표가 정확히 `(0, 0)`인 경우에만 아래 조건으로 좌표를 연결한다.

- 선택한 장소의 ID가 비어 있지 않고 응답 ID와 정확히 일치한다.
- 같은 ID를 가진 경유지가 응답에 하나만 있다.
- 선택 당시 받은 장소 좌표가 유효하다.
- 원래 최종 목적지와 기존 경유지가 유지되고, 요청한 새 경유지가 하나 추가됐다.
- 두 차례의 경로 확인을 통과한다.

이름·경유지 순서·최종 목적지 ETA로 대체하지 않는다.
응답에 유효한 다른 좌표가 있으면 선택 당시 좌표로 덮어쓰지 않는다.
ID가 없거나 다르거나 중복되면 생성하지 않는다.

이 대응은 SDK 응답 좌표를 고치는 패치가 아니다.
같은 장소임을 SDK ID로 확인해 마중에서 경유지 좌표와 ETA를 연결하는 처리다.
좌표만으로 추가한 경유지는 제공 측 수정이나 추가 검증이 필요하다.

## 예외 처리

권한 거절, 잘못된 요청, 연결 끊김, 경로 탐색 실패, 거리 제한,
좌표 누락, 기존 경로 변경, 응답 시간 초과를 구분한다.
오류가 나면 선택한 픽업 장소와 공유할 위치·ETA를 무효화한다.

- 최근 장소 조회: 8초 후 대기 종료
- 경로 응답: 12초 안에 확인되지 않으면 실패 처리, 자동 재조회는 최대 2회
- 경유지 추가 확인: 최대 45초 후 대기 종료
- 경유지 추가 같은 변경 요청은 자동으로 반복하지 않는다.

로그에는 오류 코드만 남긴다. SDK 응답·예외 메시지·좌표·초대 토큰은 기록하지 않는다.
연결 해제 뒤 도착한 이전 리스너 콜백은 세대 번호로 제외한다.

## 검증과 남은 항목

`WaypointCoordinatesTest`는 ID 일치·불일치·누락·중복, 경유지 순서 변경,
정상 좌표 덮어쓰기 방지, 잘못된 원본 좌표·ETA를 확인한다.
`NavigationRequestTest`는 요청을 한 번만 실행하고 예외 유형을 구분하는지 확인한다.

실제 에뮬레이터에서 픽업 생성 → 참여 승인 → 차량 상태 전송을 확인했다.
경유지 ETA 60초가 서버에 전달됐고, 최종 목적지 ETA 2880초는 그대로 구분됐다.
[시험 기록](evidence/waypoint-identity-2026-10-24.json)에 원본 좌표·ID·토큰을 제외한 결과를 남겼다.

[장소 ID 없는 요청 시험](evidence/waypoint-no-identity-2026-10-24.json)에서는 좌표 누락 오류,
생성 버튼 비활성화, 픽업 미생성을 확인했다. 사용자가 최종 목적지를 다시 선택한 뒤에만
그 장소로 픽업을 만들고 ETA를 전송할 수 있었다. 자동으로 최종 목적지로 바꾸지 않는다.

![공식 에뮬레이터에서 확인한 픽업 경유지](media/waypoint-selection.png)

첫 전송 시험은 에뮬레이터 시계가 서버보다 약 112초 늦어 STALE로 처리됐다.
에뮬레이터 재시작으로 시각을 동기화한 후 위 시험이 통과했다.
전송 결과가 STALE인데 화면에서 성공으로 안내하는 문제는 #14로 별도 등록했다.
SDK 경유지 도착 이벤트, 실차, 다른 내비게이션 버전은 별도 확인 대상이다.
기능 1.2 전체를 완료로 표시하지 않는다.
