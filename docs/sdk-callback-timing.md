# SDK 콜백 간격 측정

2026-10-23 · [이슈 #8](https://github.com/majung-team/majung-vehicle-app/issues/8)

## 결과

위치·목적지를 5초마다 조회하면 화면을 내려도 응답을 받았다. 정상 구간의 콜백 간격 중앙값은 약 5.01초였다.
추가 조회를 하지 않은 2분 동안은 콜백이 없었다. `onDrivingInfo`도 일정한 주기로 들어오지 않았다.

경로를 다시 요청한 뒤에는 완료 이벤트가 오지 않아 공유가 대기 상태에 머물렀다. 연결을 끊었다 다시 연결하자 복구됐다.
[재탐색 복구 이슈 #9](https://github.com/majung-team/majung-vehicle-app/issues/9)에서 이어서 확인한다.

## 조건과 수집 방법

- 공식 Pleos Connect 2.1.0 ARM64 에뮬레이터, Android API 34, NaviHelper 3.0.5.
- 같은 Mac의 로컬 API. 생성·참여·승인 후 실제 `PickupSharingService`를 실행했다.
- 공개 SDK 예제 목적지를 사용했다. 실제 도로 주행·GPS 이동·ETA 감소는 재현하지 않았다.
- 화면 중단은 `ActivityScenario`를 CREATED로 내려 `onStop`을 거치게 했다. 프로세스 강제 종료·화면 전원 OFF 시험과는 다르다.
- 5개 구간 합계 600.917초. 시험 전체 실행은 준비·정리를 포함해 604.394초였다.
- `SystemClock.elapsedRealtime`으로 현재 연결 세대가 받아들인 콜백 시각을 측정했다. 경로 탐색 중 받은 콜백도 집계하지만 공유 가능한 자료인지는 기존 앱 로직이 별도로 검사한다.
- 콜백 종류·간격·값 변경 여부와 서버의 freshness·순번 증가만 집계했다. 좌표·ETA 원문·토큰·픽업 ID는 결과 파일에 넣지 않았다.

첫 실행은 경로 제어용 권한 누락으로 8분 구간 뒤 중단됐다. debug manifest에 `NAVI_ROUTE_SEARCH`를 추가하고 전체 10분을 다시 실행했다.
이 문서와 [집계 JSON](evidence/sdk-timing-2026-10-23.json)은 재실행을 완료한 결과다. 중단된 첫 실행은 로컬 비공개 기록으로만 남겼다.
경로 제어 권한은 debug에만 추가했으며 release 권한은 바꾸지 않았다.

## 정상 구간

단위는 밀리초다. 간격은 같은 종류 콜백 사이의 시간이며, p95는 nearest-rank 방식이다.

| 구간 | 시간 | 종류 | 수신 횟수 | 중앙값 | p95 | 최대 간격 |
| --- | --- | --- | ---: | ---: | ---: | ---: |
| 추가 조회 없음·화면 활성 | 120.025초 | 위치·목적지·driving | 각 0 | — | — | — |
| 5초 조회·화면 활성 | 120.213초 | 위치 | 24 | 5,010 | 5,015 | 5,016 |
| 5초 조회·화면 활성 | 120.213초 | 목적지 ETA | 24 | 5,010 | 5,014 | 5,019 |
| 5초 조회·화면 중단 | 240.435초 | 위치 | 48 | 5,013 | 5,015 | 5,016 |
| 5초 조회·화면 중단 | 240.435초 | 목적지 ETA | 48 | 5,012 | 5,015 | 5,016 |

화면 활성·중단 구간에서 위치·목적지 값 변경은 모두 0회였다. 수신한 내용이 같아도 콜백과 heartbeat는 이어졌다.
서버를 약 2초마다 조회한 관측은 각각 FRESH 60회·120회였고, 첫·마지막 관측 사이 순번은 각각 23·47 증가했다.
이는 서버 관측 결과이며 정확한 업로드 시각의 간격 통계는 아니다.

화면 중단 구간에서 driving ETA는 1회 들어왔고 첫 수신까지 199.355초가 걸렸다. 1회뿐이므로 간격 중앙값·p95를 계산할 수 없다.
이 결과를 `onDrivingInfo`의 고정 주기로 해석하지 않는다.

## 경로 재요청과 연결 복구

| 구간 | 관측 |
| --- | --- |
| 경로 재요청·60.129초 | 약 0.222초에 ROUTE_CANCELLED, 5.381초에 ROUTE_STARTED. 완료·재탐색 종료 이벤트는 미수신 |
| 이후 SDK 조회 | 위치 요청 1회 뒤 조회가 중단됨. 마지막 위치 수신 뒤 구간 끝까지 55.467초 무수신 |
| 서버 상태 | WAITING 30회. 이전 위치·ETA를 다시 보내지 않음 |
| 명시적 해제 후·60.115초 | 서비스가 4.599초 뒤 재연결, 새 위치 9.608초 뒤 수신 |
| 복구 뒤 | 위치·목적지 각각 11회. 서버 관측 WAITING 4회·FRESH 26회, 순번 11 증가 |

현재 `DestinationReader`는 탐색 중 `pollTelemetry()`를 실행하지 않는다. 시작 이벤트 후 완료 이벤트를 받지 못하면 이 조건이 계속 남는다.
이번 시험에서는 서비스 자체는 살아 있었지만 새 자료 공유는 중단됐다. 수집 시험이 통과한 것을 경로 재요청 기능이 정상이라는 뜻으로 보지 않는다.

요청이 실제로 어떻게 처리됐는지 SDK 경로 상태와 함께 확인해야 한다. 단순 시간 초과로 `routing=false`를 만들어 이전 ETA를 보내는 방식은 피한다.
이 시험은 같은 목적지로 경로를 다시 요청한 경우다. 실제 주행 이탈에 따른 자동 재탐색을 측정한 결과는 아니다.

## 웹 끊김 표시 기준에 대한 판단

1. **5초 조회는 유지한다.** 정상 구간에서 5초 응답을 관측했고 화면 중단으로 수신 간격이 늘지는 않았다. 실차·부하 조건의 권장 최적 주기를 입증한 시험은 아니다.
2. **자동 콜백만 기다리는 방식으로 바꾸지 않는다.** 무조회 2분 동안 수신이 없었고 driving 콜백도 드물었다. 앱의 명시적 조회와 콜백을 구분해 관리한다.
3. **30초 지연·2분 중단 표시는 아직 제품 정책이다.** 이번 시험으로 실차의 정상 지연 상한이나 오탐률을 정할 수 없다. 서버의 현재 30초 만료와 새 웹의 2분 표시 정책도 따로 맞춰야 한다.
4. **명시적 무효화와 통신 지연을 나눈다.** SDK 해제·경로 변경·종료로 무효화한 값은 ‘마지막 값 흐림’ 정책으로 다시 살리지 않는다.
5. **GPS 최신성을 과장하지 않는다.** 앱이 콜백을 받은 시각은 GPS 측정 시각이 아니다. 같은 좌표 응답을 받았다고 실제 차량 위치가 새로 측정됐다고 판단할 수 없다.

성모의 웹 작업에는 정상 5초 조회 관측값과 재요청 중 WAITING 유지 사례를 전달할 근거로 사용한다.
실차·GPS 이동·실제 네트워크 단절과 복구, 30초·2분 경계의 UI 동작은 추가 시험이 필요하다.

## 다시 실행

로컬 API를 먼저 실행하고 공식 에뮬레이터의 공개 예제 경로를 준비한다. 다른 진단 앱에서 반복 조회하지 않는다.

```sh
./gradlew :vehicle:testDebugUnitTest :vehicle:assembleDebug :vehicle:assembleDebugAndroidTest :vehicle:lintDebug
# APK·시험 APK 설치, 위치 권한 허용 후
adb shell am instrument --user 10 -w \
  -e class app.majung.vehicle.SdkCallbackTimingTest -e measureSdkTiming true \
  app.majung.vehicle.test/androidx.test.runner.AndroidJUnitRunner
# 결과: 앱 내부 files/sdk-timing-summary.json
adb exec-out run-as app.majung.vehicle --user 10 cat files/sdk-timing-summary.json
```

일반 시험에서는 `measureSdkTiming=true`를 주지 않으면 10분 시험을 건너뛴다.
집계 계산은 `SdkTimingRecorderTest`에서 무수신 구간·앞뒤 공백·백분위·첫 값의 변경 미산입을 검사한다.
수신이 0회면 구간 전체가 무수신이다. 표본 1개 이하는 콜백 사이 간격을 계산하지 않고 null로 남긴다.
`maxSilenceMs`는 첫 수신 전·마지막 수신 후·콜백 사이 간격 중 가장 긴 값이다.

SDK 수신 코드의 `timingObserver`는 debug에서만 이벤트를 전달한다. release에서는 수집 파일을 만들지 않으며, Android instrumentation이 집계를 담당한다.

## 함께 확인한 검사

- 단위 시험 8개, debug·시험 APK 빌드와 lint 통과.
- 집계 계산 instrumentation 2개, 기존 SDK 픽업 흐름 2개 통과.
- 공개 예제 경로 준비 시험 1개 통과.
- release manifest에 진단용 `NAVI_ROUTE_SEARCH` 권한이 포함되지 않는 것 확인.

10분 수집이 끝난 뒤 로컬 API가 종료돼 첫 회귀 시험은 생성 단계에서 실패했다. 로컬 시험 DB로 API를 다시 실행한 뒤 기존 흐름 2개가 통과했다.
이 회귀 시험 재실행은 위 10분 집계와 별도이며, 최종 집계에는 섞지 않았다.
