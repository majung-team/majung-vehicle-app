
# Pleos SDK 콜백 간격 측정

**측정일: 2026년 10월 23일**

관련 이슈: [차량 Issue #8](https://github.com/majung-team/majung-vehicle-app/issues/8)

Pleos NaviHelper SDK의 위치·목적지·주행 정보 콜백 간격을 측정하고, 차량 화면 중단과 경로 재요청이 정보 수신 및 서버 공유에 미치는 영향을 확인한 기록이다.

공식 Pleos 에뮬레이터에서 실제 SDK를 사용했으며, 명시적 조회 여부와 Activity 중단 상태에 따라 결과를 비교했다.

> 이 측정은 에뮬레이터의 정해진 시험 경로에서 수행했다. 실제 차량 주행, GPS 이동, 실시간 교통량 변화 및 ETA 감소를 검증한 결과는 아니다.

## 1. 주요 측정 결과

| 항목 | 결과 |
| --- | --- |
| 조회 없이 2분 대기 | 위치·목적지·주행 콜백 각 0회 |
| 5초 조회 · 화면 활성 | 위치·목적지 각 24회 |
| 5초 조회 · 화면 중단 | 위치·목적지 각 48회 |
| 정상 위치 콜백 간격 중앙값 | 약 5.01초 |
| 경로 재요청 후 | 완료 이벤트 미수신 및 신규 공유 중단 |
| 경로 재요청 중 서버 | `WAITING` 30회 관측 |
| SDK 연결 해제·재연결 후 | 위치·목적지 수신 및 서버 공유 복구 |
| 전체 측정 구간 | 600.917초 |
| 전체 시험 실행 시간 | 604.394초 |

### 핵심 관찰

**명시적으로 5초마다 조회한 경우**

화면이 활성화된 상태와 중단된 상태 모두 약 5초 간격으로 위치와 목적지 ETA 콜백을 수신했다.

**추가 조회를 하지 않은 경우**

2분 동안 관련 콜백이 발생하지 않았다.

**경로를 다시 요청한 경우**

경로 시작 이벤트는 수신했지만 완료 이벤트가 오지 않았으며, 기존 구현에서는 신규 위치·ETA 공유가 대기 상태에 머물렀다.

**SDK 재연결 후**

새로운 위치·목적지 응답을 수신했고 서버 공유 상태도 복구됐다.

## 2. 시험 환경

| 항목 | 구성 |
| --- | --- |
| 차량 플랫폼 | Pleos Connect 2.1.0 |
| 실행 환경 | 공식 ARM64 에뮬레이터 |
| Android API | 34 |
| 내비게이션 SDK | NaviHelper 3.0.5 |
| 서버 | 같은 Mac의 로컬 API |
| 공유 서비스 | `PickupSharingService` |
| 경로 | 공개 SDK 예제 목적지 |
| 측정 시계 | `SystemClock.elapsedRealtime` |

실제 픽업 생성·참여·승인 후 `PickupSharingService`를 실행했다.

공개 SDK 예제 경로를 사용했으며 실제 GPS 이동이나 주행 중 ETA 변화를 재현하지 않았다.

### 화면 중단 방법

`ActivityScenario`를 `CREATED` 상태로 이동시켜 Activity의 `onStop`이 발생하도록 했다.

이 시험은 다음 상황과 구분한다.

- 앱 프로세스 강제 종료
- 사용자의 앱 강제 중지
- 디스플레이 전원 OFF
- 차량 시동 OFF/ON

Activity가 중단된 상태에서 서비스가 SDK 응답을 계속 받을 수 있는지 확인하는 시험이다.

## 3. 측정 및 집계 방식

### 측정 대상

다음 SDK 콜백을 구분하여 집계했다.

- 위치 정보 콜백
- 목적지 및 ETA 콜백
- `onDrivingInfo` 콜백

### 시간 측정

현재 연결 세대에서 받아들인 콜백의 수신 시각을 `SystemClock.elapsedRealtime`으로 측정했다.

콜백 간격은 **같은 종류의 연속된 콜백 사이 시간**으로 계산한다.

경로 탐색 중 수신한 콜백도 수신 횟수에는 포함하지만, 실제 서버에 공유 가능한 정보인지는 기존 앱의 유효성 검증 로직이 별도로 판단한다.

### 통계 기준

- 중앙값: 같은 종류 콜백 사이의 간격 중앙값
- p95: nearest-rank 방식
- 최대 간격: 관찰된 연속 콜백 사이의 가장 긴 간격
- `maxSilenceMs`: 첫 수신 전, 마지막 수신 후, 콜백 사이의 최대 무수신 시간

콜백 수신 횟수가 0회라면 전체 구간을 무수신으로 취급한다.

표본이 1개 이하인 경우에는 콜백 사이 간격을 계산하지 않고 `null`로 기록한다.

첫 번째 수신값은 비교 대상 이전 값이 없으므로 값 변경 횟수에 포함하지 않는다.

### 기록에서 제외한 정보

측정 결과에는 다음 항목만 기록했다.

- 콜백 종류 및 수신 횟수
- 수신 간격 통계
- 값 변경 여부
- 서버 freshness
- 서버 전송 순번 증가

좌표·ETA 원문, 접근 토큰 및 픽업 ID는 결과 파일에 포함하지 않았다.

## 4. 정상 조회 구간

**단위: 시간은 초, 콜백 간격은 밀리초(ms)**

| 구간 | 측정 시간 | 콜백 종류 | 수신 횟수 | 중앙값 | p95 | 최대 간격 |
| --- | ---: | --- | ---: | ---: | ---: | ---: |
| 추가 조회 없음 · 화면 활성 | 120.025 | 위치·목적지·주행 | 각 0 | — | — | — |
| 5초 조회 · 화면 활성 | 120.213 | 위치 | 24 | 5,010 | 5,015 | 5,016 |
| 5초 조회 · 화면 활성 | 120.213 | 목적지 ETA | 24 | 5,010 | 5,014 | 5,019 |
| 5초 조회 · 화면 중단 | 240.435 | 위치 | 48 | 5,013 | 5,015 | 5,016 |
| 5초 조회 · 화면 중단 | 240.435 | 목적지 ETA | 48 | 5,012 | 5,015 | 5,016 |

### 조회가 없는 경우

120.025초 동안 추가 조회를 수행하지 않았을 때 위치·목적지·주행 콜백은 발생하지 않았다.

따라서 이번 환경에서는 자동 콜백만 기다리는 방식으로 주기적인 차량 정보 공유를 유지할 수 있다는 근거를 얻지 못했다.

### 화면이 활성화된 경우

5초 간격으로 위치와 목적지를 조회한 결과 각각 24회 응답을 수신했다.

콜백 중앙값은 두 종류 모두 5,010ms였다.

### 화면을 중단한 경우

Activity가 `onStop`된 이후에도 240.435초 동안 위치와 목적지 콜백을 각각 48회 수신했다.

중앙값은 다음과 같다.

- 위치: 5,013ms
- 목적지 ETA: 5,012ms

이번 시험에서는 화면 중단으로 인해 콜백 간격이 의미 있게 늘어나는 현상을 관찰하지 않았다.

## 5. SDK 값 변경 및 서버 관측

### 위치·목적지 변경

화면 활성 및 중단 구간 모두 위치·목적지 값 변경 횟수는 0회였다.

동일한 값이 반복 수신됐지만 콜백은 계속 발생했다.

SDK에서 같은 값이 반환됐다는 이유만으로 조회나 서버 heartbeat가 중단된 것은 아니다.

다만 값이 같았다는 사실만으로 GPS가 새롭게 측정됐다고 판단할 수는 없다.

### 서버 freshness 및 순번

서버는 약 2초 간격으로 조회하여 freshness와 순번 변화를 관측했다.

| 구간 | `FRESH` 관측 | 첫·마지막 관측 사이 순번 증가 |
| --- | ---: | ---: |
| 화면 활성 · 5초 조회 | 60회 | 23 |
| 화면 중단 · 5초 조회 | 120회 | 47 |

위 수치는 서버 상태를 조회한 시점의 관측 결과다.

각 차량 정보 요청이 정확히 몇 초 간격으로 서버에 도착했는지 측정한 통계는 아니다.

### DrivingInfo 콜백

화면 중단 구간에서 `onDrivingInfo`는 1회 수신됐다.

첫 수신까지 걸린 시간은 199.355초였다.

표본이 1개이므로 콜백 간격의 중앙값이나 p95를 계산할 수 없다.

이 결과를 `onDrivingInfo`의 고정 수신 주기라고 해석하지 않는다.

## 6. 경로 재요청 후 공유 중단

이 절은 **2026년 10월 23일 당시 개선 전 구현의 측정 결과**다.

경로 재요청 과정에서 완료 이벤트가 수신되지 않아 신규 차량 정보 조회가 중단되는 현상을 확인했다.

이후 개선된 경로·목적지 재확인 방식은 별도 문서에서 관리한다.

[경로 재요청 후 공유 복구](route-recovery.md)

### 경로 재요청 측정 결과

| 구간 | 관찰 결과 |
| --- | --- |
| 경로 재요청 · 60.129초 | 약 0.222초에 `ROUTE_CANCELLED` 수신 |
| 동일 구간 | 약 5.381초에 `ROUTE_STARTED` 수신 |
| 완료 이벤트 | 경로 완료·재탐색 종료 이벤트 미수신 |
| 이후 위치 조회 | 위치 요청 1회 뒤 중단 |
| 최대 신규 위치 무수신 | 55.467초 |
| 서버 상태 | `WAITING` 30회 관측 |

### 당시 구현의 동작

`DestinationReader`는 경로 탐색 중 `pollTelemetry()`를 실행하지 않았다.

경로 시작 이벤트 이후 완료 이벤트가 도착하지 않으면 탐색 중 상태가 해제되지 않아 신규 위치·ETA 조회가 중단되는 구조였다.

이번 시험에서는 공유 서비스 자체가 종료되지는 않았다.

다만 새로운 SDK 자료를 확보하지 못해 서버 공유는 `WAITING` 상태에 머물렀다.

이전 위치나 ETA를 현재 정보처럼 재전송하지 않았다.

### 측정 해석

이 결과는 경로 재요청 이후 특정 완료 이벤트가 누락된 상황에서 당시 앱 로직이 계속 대기한 사례다.

SDK가 경로 요청을 실제로 어떻게 처리했는지, 어떤 상태에서 완료 콜백이 발생해야 하는지는 추가 확인이 필요하다.

단순히 시간 제한이 지났다는 이유로 `routing=false`를 강제로 설정하고 이전 ETA를 전송하는 방식은 사용하지 않는다.

또한 이 시험은 **같은 목적지로 경로를 다시 요청한 경우**다.

실제 주행 경로 이탈에 따른 자동 재탐색을 측정한 결과는 아니다.

## 7. SDK 연결 해제 및 재연결

경로 재요청 이후 공유가 대기 상태에 머문 상황에서 SDK 연결을 명시적으로 해제한 후 다시 연결했다.

### 측정 결과

| 항목 | 결과 |
| --- | --- |
| 측정 구간 | 60.115초 |
| 서비스 재연결 | 4.599초 후 |
| 새 위치 수신 | 9.608초 후 |
| 위치 콜백 | 11회 |
| 목적지 콜백 | 11회 |
| 서버 `WAITING` 관측 | 4회 |
| 서버 `FRESH` 관측 | 26회 |
| 서버 순번 증가 | 11 |

### 확인 내용

SDK 재연결 이후 새로운 위치·목적지 응답을 다시 받았다.

서버 관측 상태도 `WAITING`에서 `FRESH`로 복구됐다.

다만 재연결로 복구됐다는 사실만으로 경로 재요청 완료 이벤트가 수신되지 않은 원인이 확인된 것은 아니다.

## 8. 위치·ETA 공유 정책에 반영한 판단

이번 측정은 차량 정보 수집 주기와 웹 표시 정책을 검토하는 근거로 사용했다.

### 명시적 5초 조회 유지

정상 구간에서 약 5초 간격의 응답을 관찰했고, 화면 중단 상태에서도 수신 간격이 크게 변하지 않았다.

따라서 현재 구현에서는 명시적인 5초 조회를 유지한다.

이는 해당 에뮬레이터에서 확인한 결과이며, 실차·부하·절전 환경까지 포함한 최적 주기를 입증한 것은 아니다.

### 자동 콜백에만 의존하지 않음

조회하지 않은 2분 동안 위치·목적지·주행 정보 콜백이 없었다.

`onDrivingInfo`도 일정한 주기로 수신되지 않았다.

앱에서 요청한 SDK 조회와 자발적으로 전달되는 콜백을 구분하여 관리한다.

### 웹 끊김 표시 정책과 분리

당시 검토한 웹 표시 기준은 다음과 같다.

- 약 30초 지연 시 갱신 지연 표시
- 약 2분 중단 시 연결 중단 표시

이 값은 SDK 측정으로 입증된 실차 지연 한계가 아니라 제품 화면 정책이다.

서버의 당시 30초 만료 처리와 웹의 2분 표시 기준도 별도로 정합성을 확인해야 한다.

현재 운영 정책은 이후 서버·웹 구현을 기준으로 다시 확인한다.

### 무효화된 정보 재사용 금지

다음 이유로 기존 차량 정보가 무효화되면 오래된 값을 다시 활성 정보처럼 표시하지 않는다.

- SDK 연결 해제
- 경로 및 목적지 변경
- 픽업 종료
- 서버 접근 권한 종료

명시적으로 무효화한 데이터와 일시적인 통신 지연은 구분한다.

### SDK 수신 시각과 GPS 측정 시각 구분

이번 측정의 콜백 시각은 **앱이 SDK 응답을 받은 시각**이다.

실제 GPS가 위치를 측정한 시각과 동일하다고 보장할 수 없다.

같은 좌표를 다시 수신하더라도 실제 차량 위치가 새로 측정됐다고 단정하지 않는다.

## 9. 첫 시험 중단 및 재측정

최초 실행에서는 경로 제어용 권한이 누락돼 8분 구간 이후 시험이 중단됐다.

Debug Manifest에 `NAVI_ROUTE_SEARCH` 권한을 추가한 뒤 전체 10분 시험을 다시 실행했다.

### 기록 처리

- 중단된 첫 실행: 로컬 비공개 기록으로 보존
- 재실행한 전체 측정: 본 문서의 결과로 사용
- 공개 집계 JSON: 재실행 결과만 포함

경로 제어 권한은 Debug 빌드에만 추가했다.

Release Manifest에는 해당 진단 권한을 추가하지 않았다.

## 10. 측정 재실행 방법

### 사전 준비

- 공식 Pleos 에뮬레이터 실행
- 로컬 API 실행
- 공개 SDK 예제 경로 준비
- 차량 Debug APK 및 AndroidTest APK 설치
- 필요한 위치 권한 허용

같은 에뮬레이터에서 다른 진단 앱이 SDK를 반복 조회하지 않도록 한다.

### 빌드 및 검사

```sh
./gradlew \
  :vehicle:testDebugUnitTest \
  :vehicle:assembleDebug \
  :vehicle:assembleDebugAndroidTest \
  :vehicle:lintDebug
```

### 계측 테스트

기록 당시 Android 사용자 번호는 `10`이었다.

```sh
adb shell am instrument --user 10 -w \
  -e class app.majung.vehicle.SdkCallbackTimingTest \
  -e measureSdkTiming true \
  app.majung.vehicle.test/androidx.test.runner.AndroidJUnitRunner
```

`measureSdkTiming=true`를 지정한 경우에만 장시간 측정을 실행한다.

해당 인자가 없다면 일반 계측 테스트에서는 10분 측정을 건너뛴다.

여러 에뮬레이터가 연결되어 있다면 `adb -s`로 대상 기기를 명시한다.

### 결과 확인

결과는 앱 내부의 다음 파일에 저장된다.

```text
files/sdk-timing-summary.json
```

기록 당시 사용한 결과 확인 명령:

```sh
adb exec-out run-as app.majung.vehicle --user 10 \
  cat files/sdk-timing-summary.json
```

실행 환경에서 `run-as`의 사용자 지정 방식이 다른 경우에는 해당 Android 사용자의 앱 데이터 접근 방법을 확인해야 한다.

### 집계 검증

`SdkTimingRecorderTest`에서 다음 항목을 검사한다.

- 무수신 구간 처리
- 첫 수신 전과 마지막 수신 후의 공백
- 중앙값 및 백분위 계산
- 첫 수신값의 변경 횟수 제외
- 표본 부족 시 간격 통계 `null` 처리
- `maxSilenceMs` 계산

SDK 수신 코드의 `timingObserver`는 Debug에서만 측정 이벤트를 전달한다.

Release에서는 해당 수집 파일을 생성하지 않는다.

집계 자체는 Android 계측 테스트에서 수행한다.

### 회귀 시험 재실행 기록

10분 측정이 끝난 뒤 로컬 API가 종료되어 첫 회귀 시험은 픽업 생성 단계에서 실패했다.

로컬 시험 DB로 API를 다시 실행한 후 기존 SDK 픽업 흐름 2개가 통과했다.

해당 회귀 시험은 10분 SDK 콜백 측정과 별개로 수행했다.

재실행 결과를 기존 측정 통계에 합산하지 않았다.
