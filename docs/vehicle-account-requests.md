
# 운전자 계정 연결 및 다중 픽업 요청

마중 차량 앱의 운전자 계정 연결, 탑승자 요청 관리, 대기열 처리 및 오류 복구 구조를 정리한 문서다.

차량에는 운전자 계정을 연결하고, 탑승자는 모바일 웹에서 해당 운전자에게 픽업을 요청한다.

**차량 등록과 탑승자 연결은 별개다.** 한 차량에 한 명의 탑승자만 등록하는 구조가 아니며, 여러 탑승자의 요청을 받아 순서대로 처리할 수 있다.

---

## 1. 차량과 운전자 계정 연결

마중은 차량 한 대에 하나의 운전자 계정을 연결하는 것을 기준으로 한다.

하나의 운전자 계정은 여러 차량에 연결할 수 있으며, 탑승자는 차량 등록 대상에 포함되지 않는다.

### 최초 연결

1. 차량 앱에서 **휴대전화로 시작하기 · QR 만들기** 선택
2. 운전자 본인의 휴대전화로 QR코드 열기
3. 카카오 로그인 및 닉네임 설정
4. 휴대전화에서 차량 연결 요청
5. 차량에 표시된 닉네임·마중 ID 확인
6. 운전자 계정 연결 승인

기존 방식으로 등록한 차량에 운전자 계정이 연결되지 않았다면 설정의 **운전자 계정 연결 QR**을 이용한다.

QR은 발급 후 5분 동안 유효하며, 새 QR을 만들면 이전 QR은 사용할 수 없다.

차량과 운전자 계정 연결은 서비스 내 접근 권한 설정이며 실제 차량 소유권 인증을 의미하지 않는다.

[차량 최초 연결 상세 구조](vehicle-enrollment.md)

---

## 2. 탑승자의 픽업 요청

탑승자는 차량 등록 과정 없이 모바일 웹에서 운전자를 검색하고 픽업을 요청할 수 있다.

운전자와 이전에 연결한 적이 없어도 장소를 지정하여 요청할 수 있다.

### 탑승자 요청 흐름

1. [마중 웹](https://majung.cloud/account) 접속
2. 카카오 로그인
3. 닉네임 또는 마중 ID로 운전자 검색
4. 픽업 장소 선택
5. **마중 요청** 전송
6. 차량의 수락 또는 거절 대기

요청을 보낸 것만으로 차량 위치가 공개되지는 않는다.

운전자가 요청을 수락하고 실제 픽업을 시작해야 해당 탑승자의 위치·ETA 조회가 가능해진다.

---

## 3. 차량에서 요청 처리

차량 앱의 **받은 요청** 화면에서 탑승자가 보낸 요청과 대기 상태를 확인한다.

### 운전자 이용 순서

1. **받은 요청**에서 탑승자와 픽업 장소 확인
2. 요청 수락 또는 거절
3. 수락된 요청을 대기열에서 확인
4. **마중 가기**로 경로 준비
5. 최종 목적지와 기존 경유지 확인
6. SDK 경로 검증
7. 운전자가 픽업 시작 확인
8. 탑승 완료 후 다음 대기자 확인

여러 요청은 수락 순서에 따라 대기열에 등록한다.

이미 다른 픽업이 진행 중이라면 새로운 요청을 수락하더라도 즉시 다음 픽업을 시작하지 않는다.

### 순차 픽업

```text
탑승자 A 요청 ─┐
               ├── 받은 요청
탑승자 B 요청 ─┘
                     │
                     ▼
                요청 수락
                     │
                     ▼
                 대기열
                     │
                     ▼
             첫 번째 픽업 시작
                     │
                     ▼
              탑승 완료·종료
                     │
                     ▼
             다음 요청 경로 확인
                     │
                     ▼
             두 번째 픽업 시작
```

대기 중인 탑승자에게는 다른 사람의 픽업 위치나 ETA를 자신의 정보처럼 제공하지 않는다.

요청이 취소되거나 만료됐다면 다음 픽업 대상에서 제외한다.

[요청 수락부터 픽업 시작까지](request-pickup-flow.md)

## 4. 내부 코드 구성

| 파일·클래스 | 역할 |
| --- | --- |
| `VehicleAccountController.kt` | 차량 권한을 이용한 운전자 계정 연결, 요청 조회·수락·거절 |
| `VehicleAccountSection.kt` | 계정 QR, 본인 확인, 받은 요청 및 대기열 화면 |
| `PickupController.startRequested` | 수락된 요청을 기존 픽업 제어·저장·위치 공유 흐름으로 연결 |
| `MainActivity.kt` | 화면 연결 및 화면 활성 상태에서 약 10초 간격의 요청 조회 |

차량 앱의 요청 처리는 기존 픽업 기능과 별도의 시스템을 만드는 대신 `PickupController`의 기존 상태 관리 및 공유 구조를 재사용한다.

### 화면 활성 상태의 요청 조회

`MainActivity`는 화면이 활성화된 동안 약 10초 간격으로 요청 상태를 조회한다.

앱이 종료된 상태에서 새 요청을 감지해 차량 앱을 깨우는 푸시 기능은 현재 제공하지 않는다.

## 5. 주행 중 조작 제한

차량 앱은 시스템의 CarUxRestrictions를 따른다.

주행 제한 상태에서는 다음 기능을 사용할 수 없도록 처리한다.

- 차량 계정 QR 생성 및 연결
- 픽업 요청 수락·거절
- 경유지 변경
- 새로운 픽업 시작
- 계정 확인 및 승인

열려 있던 확인창도 주행 제한 상태에서는 조작할 수 없도록 처리한다.

상세 조작은 안전하게 정차한 상태에서 진행한다.

[주행 중 화면 처리](driving-summary.md)

## 6. 요청 오류 및 재접속 처리

### 6.1 연결 권한 재확인

차량 등록 권한을 확인하는 동안에는 이전 계정 QR이나 요청 처리 결과를 현재 상태에 적용하지 않는다.

서버에서 최신 등록 상태를 확인한 후 요청 처리를 이어간다.

### 6.2 요청 응답 유실

수락·거절·계정 연결 승인 요청의 응답을 받지 못한 경우 같은 쓰기 요청을 자동으로 다시 보내지 않는다.

먼저 서버 상태를 조회하여 실제 처리 여부를 확인한다.

```text
차량에서 요청 전송
        ↓
응답 수신 실패
        ↓
서버 상태 재조회
        ↓
┌──────────────────────┐
│ 요청이 처리됐는가?   │
└──────────┬───────────┘
           │
     ┌─────┴─────┐
     │           │
    완료        미완료
     │           │
     ▼           ▼
 상태 반영    사용자에게
             재확인 안내
```

통신 오류만으로 수락·거절·연결 승인 요청을 반복하지 않는다.

### 6.3 픽업 시작 응답 유실

픽업 시작 요청 후 응답을 받지 못하면 같은 요청의 결과를 서버에서 다시 확인한다.

서버는 동일한 `pickupId`에 대해 기존 픽업의 차량 접근 권한만 갱신하고, 두 번째 픽업을 생성하지 않도록 처리한다.

시작 결과가 불확실한 동안에는 일반적인 새 픽업 생성 기능을 제한한다.

### 6.4 앱 재시작 후 복구

앱을 다시 실행하면 기존 암호화 저장소의 픽업 접근 정보를 확인한다.

진행 중인 픽업이 있다면 서버에서 상태와 접근 권한을 다시 조회한다.

로컬 정보가 저장되지 않았거나 복원할 세션이 없다면 받은 요청 목록의 **진행 중인 픽업 복구**를 사용할 수 있다.

복구 후 위치 공유 재개는 기존 픽업 복구 절차에 따른다.

[픽업 저장 및 복구](pickup-recovery.md)

### 6.5 대기 요청 상태 재확인

새로운 픽업을 시작하기 전에는 다음 정보를 서버에서 다시 확인한다.

- 요청 취소 여부
- 요청 만료 여부
- 탑승자 참여 권한
- 운전자 계정 일치 여부
- 다른 활성 픽업 존재 여부
- 앞선 픽업 완료 여부

오래된 요청 목록만으로 픽업을 시작하지 않는다.

## 7. 운전자 계정 연결 확인창

운전자 계정 연결을 승인할 때는 현재 화면에 표시된 요청 ID와 마중 ID를 확인한다.

승인 대상은 화면에 표시된 연결 요청과 실제 서버 요청이 일치해야 한다.

### 요청 변경 시 처리

다음 상황에서는 기존 확인창의 승인 요청을 전송하지 않는다.

- 새로운 QR 발급
- 연결 요청 ID 변경
- 운전자 계정 변경
- 연결 대기 상태 만료
- 서버의 요청 상태 변경

기존 확인창에 표시된 사람과 실제 승인 대상이 달라지는 상황을 막기 위한 처리다.

사용자에게 계정을 다시 확인하도록 안내한다.

## 8. 테스트 및 검증 결과

이 기능은 차량 앱의 단위 테스트, 에뮬레이터 HTTP 시험 서버, 로컬 Spring 서버와 가상 계정을 사용해 검증했다.

### 테스트 결과

| 항목 | 기록된 결과 |
| --- | --- |
| 차량 앱 단위 테스트 | 35개 통과 |
| 계정 연결·화면 계측 테스트 | 3개 통과 |
| 기존 차량 등록 계측 테스트 | 6개 통과 |
| 계측 테스트 합계 | 9개 통과 |
| APK 빌드 | 성공 |

위 수치는 해당 작업 브랜치에서 수행한 시험 기록이다.

현재 `main`이나 이후 배포 버전의 전체 테스트 결과를 의미하지 않는다.

### 에뮬레이터 HTTP 시험

다음 항목을 확인했다.

- 차량 권한 전달
- 운전자 계정의 명시적 승인
- 두 요청의 목록 표시
- 요청 수락 및 거절
- 쓰기 요청 실패 시 자동 재전송 방지
- 잘못된 응답 처리

### 서버 및 웹

로컬 Spring 서버와 가상 계정을 이용하여 다음 흐름을 확인했다.

- 탑승자 요청 생성
- 요청 수락
- 대기 순서 관리
- 기존 픽업과 요청 연결
- 웹의 요청 상태 표시

### 요청 목록 화면

![가상 계정으로 확인한 차량 요청 목록](media/vehicle-account-requests.png)

HTTP 시험 서버의 가상 운전자와 탑승자 2명을 사용한 화면이다.

실제 두 대의 휴대전화나 실제 차량을 이용한 결과는 아니다.

## 9. 검증 범위 및 남은 확인

### 당시 시험에서 확인한 항목

- 차량 계정 연결 요청 및 승인
- 여러 탑승자 요청 조회
- 요청 수락·거절
- 대기열 처리
- 응답 유실 시 재조회
- 중복 픽업 생성 방지
- 로컬 세션 복구
- 주행 제한 상태의 조작 차단

### 별도 검증이 필요한 항목

- 실제 휴대전화에서 운전자 검색 및 픽업 요청
- 실제 GPS 기반 장소 선택
- 실제 두 계정 간 요청·수락 전체 흐름
- 공개 HTTPS에서의 기능별 통합 검증
- 실제 차량의 요청 및 주행 제한 동작
- 앱 종료 상태의 알림 관련 동작

이 문서의 초기 시험은 작업 브랜치와 로컬·에뮬레이터 환경을 기준으로 수행했다.

이후 기능의 `main` 반영이나 공개 서버 배포 여부는 최신 개발 현황 및 운영 기록에서 별도로 확인한다.

기존 공개 HTTPS 픽업 시험은 QR 초대 기반 흐름이었으므로 신규 탑승자 요청 검증과 구분한다.
